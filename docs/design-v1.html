📖 小说 CLI Agent — 产品设计 v1

架构参考 opencode 的 CLI Agent 范式 · 为长篇小说创作量身定制 · 2026-08-12
一句话定位:一个跑在终端里的"写作搭档"——像编程 Agent 操作代码一样,用 /命令 管理人物、世界观、时间线,用自然语言指挥 AI 写稿、改稿、查一致性;长篇小说所有状态以"文件即数据库"的形式落在作品目录里,可随时 git 版本管理。

一、功能全景(头脑风暴结果)

按优先级分三档:P0 核心决定产品能否成立;P1 重要显著提升创作质量;P2 增强锦上添花。其中一致性校验(/check)是小说 Agent 区别于"套壳聊天"的杀手锏。

📇 人物管理 /char P0

  • 人物卡片:外貌/性格/动机/背景/口头禅/秘密
  • 人物关系图谱(亲缘/同盟/敌对/暗恋…)
  • 人物出场状态:活跃/暂离/退场/死亡
  • 人设一致性校验(防崩人设)

🌍 世界观管理 /world P0

  • 设定条目:地理/历史/政治/力量体系/种族/文化
  • 条目版本记录,可回滚
  • 设定冲突检测(新条目与旧设定矛盾时提醒)
  • 按需注入:写作时只加载相关条目

✍️ 写作风格 /style P0

  • 风格预设库:网文爽文/轻小说/悬疑/严肃文学
  • 自定义风格描述 + 参数(视角/时态/句长/描写密度)
  • 范文提取风格:喂 3 段样例,生成风格指南
  • 分卷/分角色风格覆盖

📈 主角成长 /growth P0

  • 成长弧线:能力值/心性/信念的阶段性变化
  • 成长里程碑 ↔ 剧情节点绑定
  • 战力/等级体系(网文刚需)
  • 成长曲线可视化 + 停滞预警

⏳ 时间管理 /time P0

  • 自定义纪年/日历/节日系统
  • 剧情时间线:章节 ↔ 时间点映射
  • 时间线一致性校验(角色 3 天前还在 A 城,今天出现在 B 城 → 报警)
  • 剧情内倒计时事件(如"7 天后比武")

⚙️ 模型配置 /config P0

  • 多 Provider:DeepSeek/OpenAI/Anthropic/本地 Ollama
  • 任务分级:规划用强模型,批量生成用便宜模型
  • 每任务独立参数(温度/长度/seed)
  • key 管理 + 用量统计

🧩 大纲与情节 /outline P0

  • 总纲 → 卷 → 章 三层拆解
  • 情节结构:三幕/起承转合/黄金三章
  • 情节点管理(钩子/反转/高潮位置标注)
  • 伏笔管理:埋设 → 跟踪 → 回收清单

🖋 写作执行 /write P0

  • 续写/扩写/改写/重写 四种模式
  • 多版本生成,用户挑选合并
  • 卡文救援:给 3 个剧情走向选项
  • 批量生成(一次性产出 N 章草稿)

🛡 一致性校验 /check P1 ★杀手锏

  • 人设/时间线/世界观/战力 四类校验
  • 伏笔回收检查:埋了没回收的伏笔清单
  • 对话口癖/称呼一致性(叫"林晚"还是"晚晚")
  • 校验报告直接给出修改建议

🧠 记忆分层 /memory P1 ★核心难点

  • 固定层:风格 + 世界观核心 + 当前人物状态
  • 滚动层:最近 N 章全文(默认 3-5 章)
  • 按需层:大纲节点 / 时间线 / 待回收伏笔
  • 自动摘要压缩:长作品防止上下文爆炸

📚 章节与卷 /chapter P1

  • 章节状态机:草稿 → 初稿 → 修订 → 定稿
  • 字数统计 + 日更目标追踪
  • 章节标题/摘要自动生成

👁 读者视角 /reader P1

  • AI 模拟读者:毒点检测(爽点密度/节奏拖沓/降智)
  • 断章位置评估(网文追读体验)
  • 角色代入感盲测(换视角重读)

💡 灵感库 /idea P2

  • 灵感碎片速记(随时 /idea 记一笔)
  • 自动点子生成(基于现有设定)
  • 灵感 ↔ 章节/伏笔关联

📤 导出发布 /export P2

  • 导出 Markdown / TXT / EPUB / DOCX
  • 网文平台排版预处理

📊 写作统计 /stats P2

  • 字数/速度/连续创作天数
  • 燃尽图(进度 vs 目标)
  • 各模型 token 消耗账单

🔀 多线剧情 /pov P2

  • 多视角(POV)章节管理
  • 支线任务独立时间线
  • 主线/支线交叉点标注

🎙 语音写作 /voice P2

  • 语音口述 → 转写 → 整理成稿
  • 适合通勤/散步时的灵感输出

二、架构设计(参考 opencode)

opencode 的核心是 TUI + Agent 核心 + 工具层 三层:用户通过 TUI 发指令,Agent 循环(意图→上下文→LLM→工具)执行,所有状态落到文件系统。小说 Agent 完全复用这个骨架,只把"代码域工具"换成"小说域工具"。

1
TUI 交互层
终端全屏界面,支持 /命令、多行输入、流式输出、会话历史、快捷编辑。参考 opencode 的 Ink(TS) 或 Bubble Tea(Go) 实现。
2
Agent 核心(意图路由 + 上下文组装)
用户输入先走意图路由(写/改/查/管理)。写作类请求进入"上下文组装器":按当前章节、出场人物、时间点,从作品库动态拼装 prompt——这是小说 Agent 与编程 Agent 最大的不同,下文详述。
3
工具层(小说域工具集)
每个功能背后是结构化工具:char.get、world.get、timeline.check、chapter.append、vault.scan、style.load… 工具返回 JSON,让 LLM 既能生成又能精确读写状态。
4
作品库(文件即数据库)
一个作品 = 一个目录,Markdown/JSON 平铺,人类可读、git 可管、可手改。不做隐藏数据库,保证"文件在,作品就在"。

作品目录结构(核心设计)

my-novel/ # 一个作品一个目录 ├── novel.json # 作品元数据:书名/简介/当前时间点/模型绑定 ├── style.md # 风格指南(可多份,按卷切换) ├── outline/ │ ├── arc.md # 总纲 + 卷结构 │ └── plot-points.json # 情节点/钩子/高潮位置(结构化,机器可读) ├── world/ │ ├── geography.md magic.md factions.md … # 按领域拆分,按需注入 ├── characters/ │ ├── linwan.md # 每人一个文件,含元数据块(YAML front matter) │ └── relations.json # 人物关系图数据 ├── timeline.md # 纪年法 + 剧情时间线表 ├── vault.md # 伏笔台账:埋设章 / 状态 / 计划回收章 ├── chapters/ │ ├── 001.md 002.md … # 章节正文 + 头部元数据(时间/地点/出场人物/POV) ├── notes/ # 灵感碎片、废弃设定 └── .agent/ # agent 运行时状态(会话历史、索引缓存)

人物卡片 schema(示例)

--- name: 林晚 role: 主角 status: active # active / off-stage / dead appearances: [001, 002, 005] --- 外貌: 黑发及腰,左眉一道旧疤,惯穿墨色长衫 性格: 外冷内热,对承诺近乎偏执;怕黑(童年地窖) 动机: 找出兄长失踪真相,守护妹妹 能力: 剑术(三流)→ 心法突破后(一流) # growth 字段自动跟踪 口头禅: "这笔账,我记下了。" 秘密: 母亲并非死于意外(伏笔#7 关联) 关系: 师父-沈无涯(敌对?) · 妹妹-林小满(至亲) · 情敌-顾长风

三、上下文组装策略(小说 Agent 的灵魂)

编程 Agent 的上下文是"文件 + AGENTS.md + 历史";小说 Agent 必须解决 长文一致性——100 万字小说不可能全塞进上下文。方案是三层记忆 + 动态组装,每个写作请求按需拼装:

层级内容注入时机估算 Token
固定层(常驻)风格指南 + 世界观核心条目 + 当前 POV 人物档案 + 主角成长当前阶段 + 小说简介每次写作请求~3-6K
滚动层(滑动窗口)最近 3-5 章全文 + 本章大纲节点 + 上一章结尾每次写作请求~6-15K
按需层(工具查询)出场人物档案 · 当前时间点前后剧情 · 未回收伏笔 · 地点/势力设定 · 旧章节细节意图路由识别需要时,调工具注入~1-4K/次
压缩层(防爆炸)更早章节 → 摘要索引(每 10 章生成一卷摘要,可展开)超过窗口时自动触发—
设计要点:章节头部强制写结构化元数据(时间/地点/出场人物/POV/伏笔标记),这是后面 /check 一致性和上下文按需注入的数据基础——"写的时候顺手记,查的时候不用翻全文"。

四、命令体系(全量设计)

命令功能命令功能

/write续写(默认在当前时间点)/world世界观条目管理
/rewrite /expand改写 / 扩写指定段落/style风格管理 / 范文提取
/outline大纲、卷、情节节点管理/growth主角成长曲线管理
/time日历 / 时间线管理/check一致性校验(人设/时间/世界观/伏笔)
/vault伏笔埋设 / 回收 / 台账/chapter章节状态 / 字数 / 目标
/memory记忆分层查看 / 手动压缩 / 注入调试/readerAI 读者反馈 / 毒点检测
/idea灵感速记 / 点子生成/config模型 / Provider / 参数配置
/stats写作统计与账单/export导出 MD/TXT/EPUB/DOCX

自定义命令走 opencode 同款机制:.agent/commands/ 下放 Markdown 文件,定义 prompt 模板,用户可自造 /黄金三章、/断章 这类私房命令。

五、技术栈建议

方案TUI优点缺点
A. Node.js + TypeScript(推荐)Ink / React Ink生态最熟,AI 生成代码质量高,opencode 同款技术栈,开发最快启动略慢、打包稍麻烦
B. GoBubble Tea单二进制分发,性能好(opencode 的 TUI 就是 Go)UI 开发迭代慢,生态偏少
C. Rustratatui极致性能与分发开发成本最高,不推荐 MVP

存储:纯文件(Markdown + JSON)先不引入数据库,目录即数据库;等需要全文检索时再加 SQLite 索引层。

六、路线图

M1
MVP(2-3 周)
TUI + /init /write /config /chapter + 作品目录生成 + DeepSeek 接入 + 章节文件读写。此时已能"正经写小说"。
M2
设定管理(2 周)
/char /world /style /outline /time 全部落地,上下文组装器上线,写作时自动注入相关设定。
M3
质量体系(2 周)
/check 一致性校验(基于章节元数据做时间线/人设规则检查)+ /growth + /vault 伏笔台账 + /reader 毒点检测。
M4
打磨发布(持续)
/export EPUB/DOCX、/stats 账单、自定义命令市场、多作品管理、模板库。

七、待你拍板的决策点

D1 · 技术栈
Node/TS(推荐,快) / Go(分发好) / Rust(性能,不推荐 MVP)
D2 · 作品形态
单作品工作目录 vs 多作品管理(一个 CLI 管所有书,/new 切换)
D3 · 写作定位
中文网文优先(爽点/断章/毒点检测) vs 通用文学创作(风格更宽,弱化爽文指标)
D4 · 交互深度
全屏 TUI(opencode 式,沉浸) vs 轻量 REPL(启动快,命令即工具) vs 两者都要
D5 · 一致性校验的实现路线
规则引擎(元数据硬校验,快且确定) vs LLM 校验(灵活但烧 token) vs 混合(推荐:规则先行 + LLM 兜底)
